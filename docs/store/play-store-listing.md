  ```sh

  export JAVA_HOME=/opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk/Contents/Home
  export PATH="$JAVA_HOME/bin:$HOME/Library/Android/sdk/platform-tools:$PATH"
  SDK=~/Library/Android/sdk
  yes | $SDK/cmdline-tools/latest/bin/sdkmanager "emulator" \
    "system-images;android-36;google_apis_playstore;arm64-v8a"
  ```
  AVD **`upk_play_1080x2160`** already exists (Play Store image — so it can join the closed test and install the Play-signed build; `google_apis` alone has no Store). It was created from the `pixel_6` profile with `~/.android/avd/upk_play_1080x2160.avd/config.ini` overridden: `hw.lcd.width=1080`, `hw.lcd.height=2160`, `hw.lcd.density=420`, `hw.ramSize=4096`, `disk.dataPartition.size=8G`, and the `disk.dataPartition.path=<temp>` line **removed** (otherwise userdata is transient and the Play sign-in is lost on reboot).
  ```sh
  $SDK/emulator/emulator -avd upk_play_1080x2160 &
  ```
  **Installing the app on it**: `production` builds are AAB, which `adb install` refuses. Either build a `preview` APK (`eas build -p android --profile preview`, universal APK, includes arm64-v8a) or turn the AAB into a universal APK locally with bundletool (needs the same JDK 17):
  ```sh
  bundletool build-apks --bundle=upk.aab --output=upk.apks --mode=universal \
    --ks=<upload-keystore> --ks-key-alias=<alias>   # or --local-testing with a debug key
  unzip -p upk.apks universal.apk > universal.apk && adb install universal.apk
  ```
  Then:
  ```sh
  cd apps/mobile
  node scripts/capture-screenshots.mjs --platform android
  # → store/screenshots/android/{en,fr}/
  ```

## Data safety form (App content → Data safety)

Does your app collect or share any of the required user data types? **Yes.**

| Question | Answer |
|---|---|
| Data encrypted in transit? | **Yes** (HTTPS/WSS only) |
| Way to request data deletion? | **Yes** → deletion URL `https://upk-api.fly.dev/account-deletion` |

Declare **four** data types, all **collected** and none shared (corrected 2026-09-01 — the earlier two-type answer under-declared, see the ⚠ below):

| Data type | Collected | Shared | Ephemeral | Required | Purposes |
|---|---|---|---|---|---|
| Personal info → **Email address** | Yes | No | No | Yes (sign-in is mandatory) | App functionality, Account management |
| Personal info → **User IDs** | Yes | No | No | Yes | App functionality, Account management |
| Personal info → **Name** (the pseudo) | Yes | No | No | **Yes** | App functionality, Account management |
| App activity → **Other user-generated content** (saved hands) | Yes | No | No | No (optional) | App functionality |

- **Name**: Play's own definition of *Name* is "how a user refers to themselves, such as their first or last name **or nickname**", so the `pseudo` column in `users` (`apps/api/src/db.ts:41`, set via `PATCH /me`) belongs here — it is not covered by *User IDs*. It is **required**, not optional: `apps/mobile/app/_layout.tsx:46` gates the whole app behind `choose-pseudo` until a nickname exists.
- **Other user-generated content**: saved hands are **not** device-only. `apps/api/src/db.ts:49` has a `hands` table, `apps/api/src/http.ts:174` serves `GET/PUT /hands`, and `apps/mobile/src/store/useHandHistoryStore.ts` syncs them. Optional, since a user can play without ever saving a hand.
- **Game stats**: genuinely device-only (MMKV) → **not collected**.
- No analytics, ads, crash-reporting or tracking SDK exists (`apps/mobile/package.json` has none).

⚠ **The iOS `ios.privacyManifests` block in `app.json` also only declares email + user ID** — it needs the same two additions (`NSPrivacyCollectedDataTypeName`, and a user-content type) to stay consistent with Play.

⚠ **The published privacy policy contradicts this.** `apps/api/src/pages.ts:62` (fr) and `:99` (en) state that recorded hands are stored locally and "ne sont pas transmises à nos serveurs" / "is not sent to our servers", which is false since hand-history sync shipped. `/account-deletion` (`:161`, `:172`) likewise lists only email, identifiers and nickname as server data. Both pages also still describe the removed session tracker. **Play cross-checks the privacy policy against the Data safety form** — fix the pages and redeploy the API *before* submitting.

✅ **Deletion is genuinely compliant**: `deleteUserTx` (`apps/api/src/db.ts:128`) deletes the user's hands then the user row, in one transaction — no FK cascade needed. So answering "yes" to both deletion questions is truthful.

## Play Console — step-by-step first release

1. **Register** at https://play.google.com/console ($25 one-time).
   ⚠ **Account type matters**: a **personal** account must run a **closed test with at least 12 testers for 14 consecutive days** before it can apply for production access. An **organization** account (needs a D-U-N-S number) skips this. Identity verification can take a few days either way.
2. **Create app**: name `UPK – Ultimate Poker Kit`, **Game**, **Free**, accept declarations. ⚠ The app record was actually created with **fr-FR as the default language** (Console shows "Par défaut : Français (France) – fr-FR"), so **fr-FR is the mandatory locale** everywhere — store listing and release notes — and en-US is the *added* translation, not the reverse.
3. **Play App Signing** (Setup → App signing): accept the default Google-generated app signing key. The EAS keystore automatically becomes the *upload* key.
4. ⚠ **Fix Google Sign-In for Play builds** — the step that silently ruins a closed test. Play re-signs the app, so its SHA-1 differs from the EAS keystore's; without a matching OAuth client, Google Sign-In works on sideloaded APKs but **fails on the Play-distributed app** — and since sign-in is mandatory to enter UPK, testers are stuck on the login screen and the 14-day clock runs for nothing.

   **Ordering matters**: the app signing key is generated by Google at the **first AAB upload**, so this step sits *between* uploading the bundle (saved as a draft, step 9) and rolling the release out.

   1. **Find the SHA-1.** Console nav moved in 2026: *Test and release → App integrity* is now an empty shell that redirects to the new **"Protect with Play"** hub (which is about Play Integrity API / Play Billing protection — **nothing to enable there for UPK**). The Play App Signing page itself is unchanged at the URL `play.google.com/console/u/0/developers/<devId>/app/<appId>/**keymanagement**` — edit the address bar directly. Copy **"App signing key certificate" → SHA-1**. The **"Upload key certificate"** SHA-1 on the same page is the EAS keystore, which already has its client — not that one.
   2. **Create the client**: https://console.cloud.google.com → the project holding the iOS client (project number `1095846669375`) → APIs & Services → Credentials → Create credentials → OAuth client ID → **Android**, name `UPK Android (Play signing)`, package `fr.upk.app`, SHA-1 from above. Nothing to copy back — the client only needs to exist for Credential Manager to allow that package+signature pair. The id_token audience stays the **Web** client (`apps/api/src/auth/verify.ts`). Keep the existing `UPK Android` client (EAS upload key) so sideloaded APKs keep working — two Android clients, same package, different SHA-1, is the normal pattern.
   3. ⚠ **Publish the OAuth consent screen.** APIs & Services → OAuth consent screen: if *Publishing status* is still **Testing**, only accounts listed as test users can sign in (100 max) — your 12 testers get `access_denied`. Hit **Publish app**; with only `openid`/`email`/`profile` (non-sensitive scopes) no Google verification review is triggered and it takes effect immediately.
   4. **Verify on a Play-signed install before rolling out.** A sideloaded EAS APK does *not* exercise this path. Note that **Internal app sharing uses yet another key** ("Internal app sharing key certificate" on the same keymanagement page) — testing through it needs a third Android OAuth client for that SHA-1. Simpler: join the closed test yourself and install from the Play Store on the `upk_play_1080x2160` AVD (Play Store image — the emulator only fails hardware attestation, the Store itself works).
5. **Store listing** (Grow → Store presence → Main store listing): paste the en texts above, upload `icon-512.png`, `feature-graphic.png` and the `store/screenshots/android/en/` set. Then add a **French (France)** localization with the fr texts + `android/fr/` screenshots.
6. **Store settings**: category Card, contact email, website `https://upk-api.fly.dev/support`.
7. **App content** (Policy → App content): work through every section using the answers above (privacy policy, ads, app access, content rating, target audience, data safety, financial features, government/news).
8. **Build the AAB**:
   ```sh
   cd apps/mobile && eas build -p android --profile production
   ```
   Download the `.aab` from the EAS build page.
9. **Release**: Testing → Closed testing (mandatory first for personal accounts) or Production → Create release → upload the AAB → the first upload enrolls the app in Play App Signing → do step 4 now if not done → review release notes → roll out. Check the pre-launch report once bots have run the app.
10. First review typically takes a few days (sometimes longer with a simulated-gambling rating). Subsequent updates are faster.

### Later: automate uploads with `eas submit`

The **first** AAB must be uploaded through the Console UI. For updates:
1. Google Cloud Console → create a **service account**, grant it access in Play Console (Users and permissions → invite the service-account email, releases permission), download its **JSON key** (keep it out of git — e.g. `~/keys/upk-play-service-account.json`).
2. Add to `apps/mobile/eas.json`:
   ```jsonc
   "submit": { "production": { "android": { "serviceAccountKeyPath": "/Users/remy/keys/upk-play-service-account.json", "track": "production" } } }
   ```
3. Then: `eas build -p android --profile production` + `eas submit -p android --latest`.
